\webtraffic{} \citep{early2024millet} is synthetic, so the generator knows which time steps it
changed to create each class. That is the last column of \Cref{tab:datasets}, and it is why
\webtraffic{} is the only place NDCG@$n$ can be computed at all; on \ucr{} \citep{dau2019ucr} I can
only measure AOPCR. \webtraffic{} is also small and fast, so I used it as my screening set: every
new encoder or head is tried there first and only the promising ones go on to the slow \ucr{} sweep.
\Cref{sec:res:ucr} shows the price of that choice. \citet{early2024millet} published \millet{}
results on 85 of the 128 \ucr{} datasets, so I run that same 85 to make a dataset-by-dataset
comparison possible, plus the remaining 43 so the result does not rest on one convenient subset.

\subsection{Baselines and training protocol}
\label{sec:setup:baselines}

I compare against FCN, ResNet \citep{wang2017fcn} and InceptionTime \citep{fawaz2020inceptiontime},
each paired with \millet{}'s own Conjunctive head. I did not quote the numbers printed in the
papers; I re-trained all three myself through the same pipeline and the same recipe as \seanet{}.
That was the most important methodological decision of the internship, because a published number
mixes the architecture with whatever recipe its authors used. Re-training removes the doubt: any gap
between \seanet{} and a re-trained baseline is down to the architecture. The recipe really does
matter, and I can show it rather than assert it -- I also set up a run that uses \millet{}'s own
published hyperparameters on my harness, and on \webtraffic{} the identical architecture scores
0.887 with my recipe against 0.920 with theirs (\Cref{sec:disc:reading}). That is why published
\millet{} numbers always stay in their own column in \Cref{sec:results}.

\label{sec:setup:protocol}
Every model, mine and baseline alike, is trained with the recipe in \Cref{tab:protocol}, so the
numbers in \Cref{sec:results} differ only because of the model.
Two settings adapt to the dataset instead of being fixed, because the \ucr{} archive spans 40 to
24{,}000 series: I hold out a 20\,\% validation split only when a dataset has at least 100 training
series (below that the split would be too noisy, so I watch the training loss instead), and the
batch size scales with the training set, since a fixed 16 would be more than half of the smallest
\ucr{} datasets. Seeds changed during the internship: the first sweep was single-seed because 72
variants times 129 datasets was already close to my compute budget, and once the interesting models
were known I went back and added two more seeds to the four models that carry the argument of this
report. So there are real variance estimates exactly where the claims are made, and single-seed
numbers everywhere else. Every table says which is which.

\subsection{The experimental pipeline I built}
\label{sec:setup:pipeline}

\begin{contribution}
The whole experimental pipeline -- configuration system, model registry, resumable sweeps, results
store, figure and table generation, experiment tracking -- is my own work. It is what made it
possible to train and compare 72 model variants over 129 datasets inside the internship.
\end{contribution}

A model is always \emph{encoder + pooling head}, and both are chosen by name in a small
configuration file rather than hardcoded. Two registries, one for encoders and one for heads, map a
name to the matching class, and a builder wires the two together. This is what let 72 variants exist
without 72 copies of nearly identical training code: every new row in the results tables is a new
configuration file, not a new script. The five ablation settings in \Cref{app:ablations} are a good
example -- each is a copy of an existing file with one line changed.

Each model writes into its own results folder, one row per dataset per seed, so two models can never
overwrite each other. Grid'5000 jobs have a wall-clock limit and a full sweep does not always finish
inside it, so every model keeps a list of the datasets it has already finished; restarting the same
job skips those, and a killed job costs at most the one dataset that was mid-training. Every run is
also logged to MLflow and saves its per-epoch loss curve, so the curve travels with the results when
they are copied off the training machine. Finally, every figure and \LaTeX{} table in this report is
generated from those stored results by a single command (\Cref{app:commands}), which is what lets me
say no number here was typed in by hand.

The stack is PyTorch \citep{paszke2019pytorch} for the models, MLflow for tracking, Optuna
\citep{akiba2019optuna} for the search in \Cref{app:extra}, Git, and \LaTeX{}. Development and smoke
tests happened locally on Windows; every real run happened on Grid'5000 Linux GPU nodes. The two
environments differ in more than the operating system (\Cref{app:env}), so the same configuration
files are used on both sides to keep the one thing that must not drift identical between them.
