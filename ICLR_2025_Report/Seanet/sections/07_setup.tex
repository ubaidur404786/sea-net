\section{Experimental Setup}
\label{sec:setup}

% ---------------------------------------------------------------------
\subsection{Datasets}
\label{sec:setup:data}

\paragraph{\webtraffic{}.}
\webtraffic{} is a synthetic dataset introduced by \citet{early2024millet} for exactly this kind of
work. Unlike a real dataset, the generator knows which time steps it modified to create each class,
so those steps can be used as ground truth to score an explanation instead of only trusting it by
eye. It has 1{,}000 series in total (500 for training, 500 for test), each of length 1{,}008, spread
over 10 classes.

Because it is small and fast to train -- a couple of minutes per model on a GPU -- I used it as my
screening set. Every new encoder or pooling head is tried here first, and only the promising ones go
on to the much slower \ucr{} sweep. \Cref{sec:res:ucr} shows the price of that choice, so I want to
be clear that it was a compute decision, not a claim that \webtraffic{} predicts \ucr{}.

\paragraph{\ucr{} archive.}
The \ucr{} archive \citep{dau2019ucr} holds 128 univariate time series datasets, from tiny
(16 training series) to large (almost 9{,}000), and from short (15 time steps) to long (nearly
2{,}900). \citet{early2024millet} published \millet{} results on 85 of these 128, so I run every
model on that same 85 first, which is what makes a dataset-by-dataset comparison against their
numbers possible. I also run the remaining 43, so the headline result does not rest on one
convenient subset.

place where NDCG@$n$ can be computed at all, because it is the only place where I know the right

the model itself, not against the truth.

\subsection{Baselines}
\label{sec:setup:baselines}

I compare against three backbones: FCN, ResNet \citep{wang2017fcn}, and InceptionTime
\citep{fawaz2020inceptiontime}, the one \millet{} itself uses. All three are paired with \millet{}'s
own Conjunctive pooling head, and -- this is the part that matters -- all three are trained through
the exact same pipeline and recipe as \seanet{}: same optimiser, same epoch budget, same early
stopping, same data splits.

I did not simply quote the numbers printed in the paper, and I think that was the most important
methodological decision of the internship. A published number is a mix of the architecture
\emph{and} whatever recipe that paper's authors used. If I only quoted it, I could not tell whether
a difference in my results comes from the architecture or from a different number of training
epochs. Re-training the baselines myself removes that doubt: any gap between \seanet{} and a
re-trained baseline is down to the architecture, because everything else is held fixed.

The recipe really does matter, and I can now show it rather than assert it. I also built
\texttt{configs/models/sv1/millet\_paper.yaml}, which reproduces \millet{}'s own published
hyperparameters (1500 epochs, no weight decay, no label smoothing, no validation split) on my
harness. On \webtraffic{} the identical architecture scores 0.887 with my recipe and 0.920 with
theirs (\Cref{sec:disc:reading}). That is why the published \millet{} numbers always stay in their
own column in \Cref{sec:results} and are never averaged or merged with a number I produced.

\subsection{Training protocol}
\label{sec:setup:protocol}

Every model in this study -- \seanet{} and every baseline -- is trained with the same recipe
(\texttt{seanet/train.py}), so the numbers in \Cref{sec:results} differ only because of the model
and not because of the training setup.

I minimise a label-smoothed cross-entropy loss with Adam, for up to 400 epochs, and stop early once
60 epochs pass with no improvement in the loss I am watching. When a dataset has at least 100
training series I hold out a stratified 20\,\% validation split and watch the validation loss. On
the smaller \ucr{} datasets a 20\,\% split would be a handful of series and too noisy to trust, so I
watch the training loss instead. The batch size scales with the dataset (a tenth of the training
set, capped at 16, floor of 2), because a fixed batch size of 16 would be more than half of the
whole training set on the smallest \ucr{} datasets.

A word about seeds, because it changed during the internship. The first full sweep was single-seed:
72 model variants times 129 datasets was already close to my compute budget, and running each one
three times was not possible in the time available. Once the sweep was finished and the interesting
models were known, I went back and added two more seeds to the four models that carry the argument
of this report. Two of them also have all three seeds over the whole \ucr{} archive. So the report
has real variance estimates exactly where the claims are made, and single-seed numbers everywhere
else. I say which is which in every table, and \Cref{sec:disc:reading} explains what that means for
how confidently a difference can be read.

\subsection{Metrics}
\label{sec:setup:metrics}

I report three groups of numbers for every model.

\emph{Classification}: test accuracy and cross-entropy loss.

\emph{Explanation quality}: AOPCR and NDCG@$n$ (\Cref{sec:bg:metrics}). NDCG@$n$ is computed only on
\webtraffic{}, since it is the only dataset with per-step ground truth.

\emph{Cost}: parameter count and saved model size for every model, plus FLOPs, inference latency and
peak memory measured at the real \webtraffic{} shape (\texttt{results/SEA\_NET/profile.csv}).
Reporting cost next to accuracy matters, because a bigger model can win on accuracy by brute force
alone. Without the parameter column a reader cannot tell whether a gain came from a better idea or
just from more capacity.

One warning about AOPCR, which is the single easiest number in this report to misread. AOPCR is not
normalised: it depends on the scale of the model's own logits, so my AOPCR values are only
meaningful \emph{relative to each other}, never as an absolute value against a number from another
paper -- including \millet{}'s published AOPCR. \Cref{sec:disc:reading} shows a direct measurement
of how large that scale effect is.

\subsection{The experimental pipeline I built}
\label{sec:setup:pipeline}

\begin{contribution}
The whole experimental pipeline -- configuration system, model registry, resumable sweeps, results
store, figure and table generation, experiment tracking -- is my own work. It is what made it
possible to train and compare 72 model variants over 129 datasets inside the internship.
\end{contribution}

A model is always \emph{encoder + pooling head}, and both are chosen by name in a config file
(\texttt{configs/models/<model>.yaml}) rather than hardcoded. Two small registries
(\texttt{seanet/features.py} for encoders, \texttt{seanet/pooling.py} for heads) map a name like
\texttt{sea\_mstcn\_sep\_gated} or \texttt{sea\_topk\_conjunctive} to the matching class, and
\texttt{build\_model\_from\_config} looks up both and wires them together. This is what let 72 model
variants exist without 72 copies of nearly identical training code: every new row in the results
tables is a new YAML file, not a new script. The five ablation configs in \Cref{app:ablations} are a
good example -- each is a copy of an existing file with one line changed.

Each model writes into its own results folder under \texttt{results/SEA\_NET/<model>/}, one row per
dataset per seed in \texttt{results.csv}, so two models' numbers can never overwrite each other.

Grid'5000 jobs have a wall-clock limit, and a full sweep over 129 datasets does not always finish
inside it. Every model tracks which datasets it has already finished in a small
\texttt{done\_train\_dataset.txt} file. Restarting the same command skips anything already done and
picks up where it stopped, so a killed job costs at most the one dataset that was mid-training, not
the whole sweep. Every run is also logged to MLflow, and each run now writes its per-epoch loss
curve to \texttt{results/SEA\_NET/<model>/curves/} so the curve travels with the results when they
are copied off the training machine.

Finally, every figure and \LaTeX{} table in this report is generated from the stored
\texttt{results.csv} files by one command (\texttt{python main.py paper}). That is what lets me say
no number in this report was typed in by hand.

The stack is PyTorch \citep{paszke2019pytorch} for the models, MLflow for experiment tracking,
Optuna \citep{akiba2019optuna} for the hyperparameter search in \Cref{app:extra}, Git for version
control, and \LaTeX{} for this report. Day-to-day development and small smoke tests happened locally
on Windows; every real training run happened on Grid'5000 Linux GPU nodes. The two environments
differ in more than the operating system -- Python and package versions, and how a job is started (a
local terminal against an \texttt{oarsub} submission) -- so the same \texttt{configs/*.yaml} files
are used on both sides, to keep the one thing that must not drift identical between them.
