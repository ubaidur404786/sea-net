\section{Proposed Architecture: \seanet{}}
\label{sec:architecture}

\begin{contribution}
The encoder described in this section is my own design. It replaces the InceptionTime backbone used
by \millet{} while keeping exactly the same interface, so any encoder can be paired with any pooling
head and the comparison stays fair.
\end{contribution}

% ---------------------------------------------------------------------
\subsection{Design goals}
\label{sec:arch:goals}

I set five goals before writing any code, and every choice later in this section points back to one
of them.

\begin{enumerate}\itemsep3pt
  \item[\textbf{G1}] \textbf{Smaller.} Clearly fewer parameters than InceptionTime, small enough to
        be a realistic microcontroller target (\Cref{sec:context}).
  \item[\textbf{G2}] \textbf{At least as accurate}, under an identical training recipe.
  \item[\textbf{G3}] \textbf{Length-preserving.} One embedding per time step, always. The
        interpretation has one value per time step and AOPCR masks single time steps, so the length
        $\nsteps$ must never change inside the encoder.
  \item[\textbf{G4}] \textbf{Local.} Each time step's embedding must stay tied to a limited window.
        If a single output can be built from evidence spread over the whole series, the importance
        map smears out and stops being useful.
  \item[\textbf{G5}] \textbf{Modular.} Encoder and pooling head must be swappable from a config
        file, so any pair can be trained without touching code.
\end{enumerate}

% ---------------------------------------------------------------------
\subsection{Overview}
\label{sec:arch:overview}

\seanet{} follows the same two-stage template as \millet{} (\Cref{sec:bg:millet}): a raw series goes
in, an encoder turns it into one embedding per time step, and a MIL pooling head turns those
embeddings into a class prediction plus an explanation.

A batch of $B$ series of length $\nsteps$ enters as $(B, 1, \nsteps)$ -- one input channel, because
every dataset in this report is univariate. The encoder (\Cref{sec:arch:block}) is a stack of
multi-scale depthwise-separable residual blocks whose dilation grows but is capped (goal~G4). It
turns the input into one $\dmodel$-wide embedding per time step, $(B, \dmodel, \nsteps)$, which is
exactly \Cref{eq:encoder_generic}.

This is the only place \seanet{} changes \millet{}. The pooling head afterwards is one of the heads
of \Cref{sec:pooling} -- the \millet{} Conjunctive baseline, or one of my own -- unchanged in shape.
It reads the $(B, \dmodel, \nsteps)$ embeddings and returns the bag logits $(B, \nclz)$ and the
interpretation $(B, \nclz, \nsteps)$. Every encoder in this section follows that same input/output
contract, which is what makes goal~G5 possible.

\subsection{The multi-scale separable block}
\label{sec:arch:block}

This block is the heart of the encoder. Let $\mathbf{h} \in \R^{\dmodel \times \nsteps}$ be its
input and $\delta$ its dilation. Write $D_k^{(\delta)}$ for a depthwise convolution of kernel size
$k$ and dilation $\delta$ (one filter per channel), and $P$ for a pointwise $1\times1$ convolution
(which mixes the channels). One \emph{unit} is
\begin{equation}
  \mathcal{U}(\mathbf{h})
  = \operatorname{Drop}\Big(\operatorname{ReLU}\Big(\operatorname{BN}\Big(
      P\Big(\textstyle\sum_{k \in \mathcal{K}} D_k^{(\delta)}(\mathbf{h})\Big)\Big)\Big)\Big),
  \qquad \mathcal{K} = \{5, 11, 23\},
  \label{eq:unit}
\end{equation}
and one block runs two units and adds the input back:
\begin{equation}
  \operatorname{Block}(\mathbf{h}) = \operatorname{ReLU}\big(\mathbf{h} +
  (\mathcal{U} \circ \mathcal{U})(\mathbf{h})\big).
  \label{eq:block}
\end{equation}
Zero ``same'' padding is used everywhere, so the length $\nsteps$ never changes (goal~G3). Block $i$
uses $\delta_i = \min(2^i, \delta_{\max})$, which grows the receptive field quickly but keeps it
local (goal~G4).

In words, \Cref{eq:unit} looks at the same signal at three time scales at once. A kernel of size 5
sees a narrow local pattern, a kernel of size 23 sees about four times as far, and their outputs are
simply added, so the block does not have to pick one scale in advance. The pointwise convolution $P$
that follows does not look at time at all -- it only mixes the $\dmodel$ channels at each time step,
combining what the three kernels found. BatchNorm \citep{ioffe2015batchnorm} keeps the activations on
a stable scale, ReLU adds the non-linearity, and dropout regularises. Every convolution in
\Cref{eq:unit} is \emph{depthwise} -- one filter per channel -- which is what makes the whole step
cheap.

\paragraph{Why this is small.}
A standard convolution with $\dmodel$ input and output channels and kernel size $k$ costs
$\dmodel^2 k$ weights. A depthwise-separable pair costs only
\begin{equation}
  \underbrace{\dmodel k}_{\text{depthwise}} \;+\; \underbrace{\dmodel^2}_{\text{pointwise}}
  \;\ll\; \dmodel^2 k .
  \label{eq:sep_cost}
\end{equation}

Counting the weights of \Cref{eq:unit} directly from the code, with the base width $\dmodel = 128$
and kernels $\{5,11,23\}$: the three depthwise convolutions together cost
$\dmodel \cdot 6 + \dmodel \cdot 12 + \dmodel \cdot 24 = 5{,}376$ weights, counting one bias per
channel. The pointwise convolution alone costs $\dmodel^2 + \dmodel = 16{,}512$ -- already three
times more than all three depthwise convolutions put together. Adding BatchNorm's $2\dmodel = 256$,
one unit costs $22{,}144$ parameters, one block (two units) costs $44{,}288$, and the full six-block
encoder plus its stem costs about $266{,}752$. That matches the $269{,}083$ measured for the wide
base model in the leaderboard, the small remainder being the pooling head.

A standard, non-separable convolution looking at the same three kernel sizes would instead cost
$\dmodel^2 \cdot (5{+}11{+}23) = 638{,}976$ weights for that same step -- about $29\times$ more.
That factor is why goal~G1 is reachable at all.

\subsection{Encoder variants}
\label{sec:arch:variants}

I built several encoders on top of the same block. Each paragraph below follows the same shape: the
problem it attacks, the change in one equation, and what I expected. The results are in
\Cref{sec:results}, not here. \Cref{tab:encoder_variants} in the appendix lists all of them side by
side with the parameter count of each, so this section can stay about the ideas.

\paragraph{Bottleneck.}
The pointwise $1\times1$ convolution dominates the parameter count, because it costs $\dmodel^2$.
So I factorise it through a narrower rank $r < \dmodel$:
\begin{equation}
  P = P_2 P_1, \qquad P_1 \in \R^{r \times \dmodel}, \quad P_2 \in \R^{\dmodel \times r},
  \qquad \text{cost } \dmodel^2 \rightarrow 2\dmodel r .
  \label{eq:bottleneck}
\end{equation}
With the ratio 4 I used, we get $r = \dmodel/4$, so the pointwise cost drops from $\dmodel^2$ to $\dmodel^2/2$ -- exactly half, whatever $\dmodel$ is.
At the size actually used in the experiments ($\dmodel = 64$, 4 blocks), this cuts the full model
from 57{,}580 to 41{,}324 parameters, a real 28\,\% saving on the whole encoder and not just on the
pointwise step. This is the cheapest encoder I built, and it is the one in my headline result.

\paragraph{Gated.}
Not every channel matters for every series. A summary over time drives a channel gate:
\begin{equation}
  \bar{\mathbf{h}} = \tfrac{1}{\nsteps}\textstyle\sum_j \mathbf{h}_{:,j},
  \qquad
  \mathbf{h}' = \mathbf{h} \odot \sig(W_g \bar{\mathbf{h}}),
  \label{eq:gate}
\end{equation}
where $\odot$ multiplies element by element. This lets the whole-series context decide which feature
channels to trust, without touching individual time steps. The gate multiplies by
$(1+\text{gate}) \in [1,2]$ rather than replacing the features outright, so the per-time-step
differences that AOPCR and NDCG depend on are never flattened -- only the channels are turned up or down, never the time axis.
The code offers three ways to summarise time into that one vector (max, mean, or the last time step)
and I trained all three under the same recipe so they could be compared.

\paragraph{Input gate.}
Same idea, but the gate is read straight from the raw input instead of from the deep features:
\begin{equation}
  g_j = \sig\!\big(W_g \ast \bag\big)_j \in [0,1]^{\dmodel},
  \qquad
  \mathbf{h}'_j = \mathbf{h}_j \odot (1 + g_j) ,
  \label{eq:input_gate}
\end{equation}
where $W_g \ast \bag$ is a small convolution (kernel size 7) applied to the raw series. The
difference from the Gated variant is exactly this: \Cref{eq:gate} builds \emph{one} gate for the
whole series from the deep features, while \Cref{eq:input_gate} builds a gate that changes at
\emph{every} time step, read from the raw signal. I tried both because they attack the same idea at
two different granularities -- coarse (whole series) against fine (per time step) -- and comparing
them says which granularity the gating idea actually needs.

\paragraph{Spike / trend.}
Two branches: a smoothed trend branch and a high-pass spike branch, mixed and then gated.
\begin{align}
  \text{trend}_j &= \text{mstcn\_sep}(\bag)_j \in \R^{\dmodel} ,
  \label{eq:spike_trend}\\
  \text{spike}_j &= \operatorname{ReLU}\!\big(\operatorname{BN}(\operatorname{Conv1d}_3(
  \bag - \operatorname{avg}_w(\bag)))\big)_j \in \R^{d_{\text{spike}}} ,
  \label{eq:spike_branch}\\
  \mathbf{h}_j &= P_{1\times 1}\big([\text{trend}_j \,;\, \text{spike}_j]\big) \in \R^{\dmodel} .
  \label{eq:spike_mix}
\end{align}
The trend branch is the usual encoder, unchanged. The spike branch first removes a local moving
average $\operatorname{avg}_w$ (window 5) from the raw series, so what is left is near zero on smooth
stretches and large only where the signal jumps, and a small convolution turns that into
$d_{\text{spike}} = 16$ extra channels. The two branches are concatenated and mixed back to width
$\dmodel$. My idea was that on some datasets the evidence is one sharp point rather than a slow
trend, and a dedicated branch should find it. \Cref{tab:ablation_encoder} shows this was the weakest
of my real encoders, so the idea did not pay off.

\paragraph{Reconstruction residual.}
This one asks a different question: what does the encoder \emph{fail} to explain? A $1\times1$
convolution rebuilds the input from the trend features, the rebuilt version is subtracted from the
real input, and the leftover residual is turned into $d_{\text{res}} = 16$ extra channels which are
mixed back in:
\begin{equation}
  \widehat{\bag} = P_{\text{rec}}(\text{trend}), \qquad
  \mathbf{h}_j = P_{1\times1}\big([\,\text{trend}_j \,;\, \phi(\bag - \widehat{\bag})_j\,]\big).
  \label{eq:recon}
\end{equation}
The residual $\bag - \widehat{\bag}$ marks the parts of the signal the smooth features could not
account for, which is a reasonable place to look for an unusual event. There is no separate
reconstruction loss: the branch is learned end to end, so it is really a learned residual feature.
It turned out to be the second strongest encoder in my ablation (\Cref{tab:ablation_encoder}).

\paragraph{Multi-scale channels (a wrapper, not an encoder).}
Rolling max, min and standard deviation over several windows are appended as extra input channels,
so the network gets local statistics for free:
\begin{equation}
  \bag^{+} = \Big[\, \bag \,;\; \big(\text{roll\_max}_w(\bag)\big)_{w \in \mathcal{W}} \;;\;
  \big(\text{roll\_min}_w(\bag)\big)_{w \in \mathcal{W}} \;;\;
  \big(\text{roll\_std}_w(\bag)\big)_{w \in \mathcal{W}} \;;\; \operatorname{sign}(\Delta \bag) \,\Big] ,
  \label{eq:mschan}
\end{equation}
with $\mathcal{W} = \{3,7,15,31\}$ (all odd, so each window stays centred) and
$\Delta \bag_j = \bag_j - \bag_{j-1}$. This wrapper does not replace an encoder. It only widens the
input from 1 channel to $1 + 4 \cdot 3 + 1 = 14$ channels before handing it to any encoder above.
I used max, min and standard deviation rather than a rolling mean on purpose: a mean is a
\emph{linear} operation the stem convolution could already learn by itself, while max, min and
standard deviation are non-linear and genuinely add something a convolution cannot compute. One
BatchNorm is applied to the 14 channels first, because they do not share the raw series' scale --
a rolling max sits high, a rolling standard deviation is small and always positive. I tried skipping
that normalisation and it cost accuracy.

\paragraph{Multi-scale pyramid (a wrapper, not an encoder).}
The same encoder runs on the series downsampled by 1, 2, 4 and 8; the outputs are stretched back to
length $\nsteps$ and fused:
\begin{equation}
  \mathbf{h}_j = \sum_{s \in \mathcal{S}} \alpha_j^{s} \, \mathbf{h}_j^{(s)} ,
  \qquad
  \alpha_j^{s} = \operatorname{softmax}_{s}\big(\text{score}(\mathbf{h}_j^{(s)})\big),
  \qquad \sum_{s \in \mathcal{S}} \alpha_j^{s} = 1 ,
  \label{eq:pyramid_fusion}
\end{equation}
where $\mathcal{S} = \{1,2,4,8\}$ and the softmax normalises over the \emph{scale} axis, never over
time, so the per-time-step signal AOPCR and NDCG need is untouched. One encoder is shared across
every scale, so the parameter count barely moves; the extra cost is mostly compute (about
$1.9\times$). This was my attempt at the 1-D version of multi-magnification whole-slide-image MIL
\citep{hashimoto2020msdamil}, and it is the weakest thing I built
(\Cref{tab:ablation_encoder}). One constraint was needed to make it work at all: the wrapped encoder
must stay shallow enough that its receptive field does not exceed $\nsteps / \max(\mathcal{S})$,
otherwise the coarsest scales collapse to a nearly constant signal and the interpretation degrades
badly. That is why the pyramid setting uses a shallow 2-block base with the smallest dilation, and
why the pipeline checks this automatically for any new combination.

\subsection{Why this design and not another}
\label{sec:arch:why}

I considered three other directions and rejected each for a concrete reason.

A \textbf{Transformer encoder} was the most obvious alternative to a convolutional stack. I rejected
it for two reasons. Full self-attention costs $\mathcal{O}(\nsteps^2)$ in time and memory, and the
series here run to 1000--1500 time points, which is far too expensive for the microcontroller target
of this internship (\Cref{sec:context}). Just as important, unrestricted attention lets any time step
attend to any other, which works directly against goal~G4: a single output could then be built from
evidence smeared over the whole series, and the importance map would be much harder to trust.

\textbf{Pruning or quantising InceptionTime} was the second option. Pruning does shrink a network,
but it does nothing about the real problem from \Cref{sec:bg:tsc}: InceptionTime still ends in global
average pooling, which destroys the per-time-step information before the classifier sees it. A pruned
InceptionTime would still need a separate post-hoc explainer, with the same faithfulness problem.

\textbf{Keeping a bigger, more accurate backbone and explaining it afterwards} was the third. I
rejected it for the same reason \millet{} does: a post-hoc explanation is not guaranteed to match
what the model actually computed (\Cref{sec:bg:related}). Every encoder in this section keeps the MIL
contract of \Cref{eq:encoder_generic} exactly, so any pooling head from \Cref{sec:pooling} can turn
it into a faithful, built-in explanation instead.
