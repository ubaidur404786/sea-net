\section{Proposed Architecture: The \seanet{} Encoder}
\label{sec:architecture}

\begin{contribution}
The encoder described in this section is my own design. It replaces the InceptionTime backbone used
by \millet{} while keeping exactly the same interface, so any encoder can be paired with any pooling
head and the comparison stays fair.
\end{contribution}

% ---------------------------------------------------------------------
\subsection{Design goals}
\label{sec:arch:goals}

I set five goals before writing any code, and every choice later in this section points back to one
of them.

\begin{enumerate}\itemsep2pt
  \item[\textbf{G1}] \textbf{Smaller} than InceptionTime, small enough to be a realistic
        microcontroller target (\Cref{sec:context}).
  \item[\textbf{G2}] \textbf{At least as accurate}, under an identical training recipe.
  \item[\textbf{G3}] \textbf{Length-preserving.} One embedding per time step, always: the
        interpretation has one value per time step and AOPCR masks single time steps, so $\nsteps$
        must never change inside the encoder.
  \item[\textbf{G4}] \textbf{Local.} Each embedding must stay tied to a limited window. If one
        output can be built from evidence spread over the whole series, the importance map smears
        out and stops being useful.
  \item[\textbf{G5}] \textbf{Modular.} Encoder and pooling head swappable from a config file, so any
        pair can be trained without touching code.
\end{enumerate}

% ---------------------------------------------------------------------
\subsection{Overview}
\label{sec:arch:overview}

\seanet{} keeps the two-stage MIL template of \Cref{sec:bg:millet} -- encoder, then pooling head --
and changes only the encoder. \Cref{fig:arch_overall} shows the whole model, and it is worth reading
once before the equations.

Follow it left to right. A batch of $B$ series enters as $(B, 1, \nsteps)$: one input channel,
because every dataset here is univariate. A \textbf{stem} convolution lifts that single channel to
$\dmodel$ channels, giving $(B, \dmodel, \nsteps)$. A stack of \textbf{multi-scale separable
residual blocks} (\Cref{sec:arch:block}) then refines those features. Each block looks a little
further back than the one before it, because its dilation doubles -- $1, 2, 4, 8, 16, 16$ -- but the
doubling stops at 16, which is what keeps every embedding tied to a limited window (goal~G4). No
block ever changes the length, so the output is still $(B, \dmodel, \nsteps)$: one embedding
$\emb_j$ per time step, which is exactly \Cref{eq:encoder_generic} and exactly what goal~G3 asks
for.

Everything after that point is the pooling head, and it is unchanged from \millet{} in shape. The
head drawn in the figure is Top-$k$ class-wise conjunctive pooling, my best one
(\Cref{sec:pool:topk}); the important thing here is only its interface. It reads the
$(B, \dmodel, \nsteps)$ embeddings and returns two things: the class prediction $(B, \nclz)$, and
the interpretation $(B, \nclz, \nsteps)$ -- one importance value per class per time step, taken from
the same numbers that produced the prediction. Because every encoder in this section respects that
same input/output contract, any encoder can be paired with any head from a config file, which is
goal~G5.

\subsection{The multi-scale separable block}
\label{sec:arch:block}

This block is the heart of the encoder, and it rests on two standard ideas.
\emph{Dilated} convolutions, from Temporal Convolutional Networks \citep{bai2018tcn}, let the filter
skip over points so its window widens fast without extra weights. \emph{Depthwise-separable}
convolutions \citep{chollet2017xception, howard2017mobilenets} split one convolution in two: a cheap
step that filters each channel on its own, then a cheap $1\times1$ step that mixes the channels. My
block combines both and adds a third thing of its own -- three kernel sizes running in parallel.

\paragraph{How to read the equations.}
Everything below uses five symbols, and they mean the same thing every time they appear.

\begin{center}\small
\begin{tabular}{@{}l@{\quad}p{0.76\linewidth}@{}}
\toprule
$\mathbf{h} \in \R^{\dmodel \times \nsteps}$ & the features inside the block: $\dmodel$ channels,
one column per time step \\
$D_k^{(\delta)}$ & \emph{depthwise} convolution, kernel size $k$, dilation $\delta$. One filter per
channel, so it looks at \emph{time} but never mixes channels \\
$P$ & \emph{pointwise} $1\times1$ convolution. It mixes the $\dmodel$ channels at one time step, and
never looks at time \\
$\mathcal{K} = \{5,11,23\}$ & the three kernel sizes run side by side in every block \\
$\delta$ & the dilation of this block: how far apart the filter taps sit \\
\bottomrule
\end{tabular}
\end{center}

So a depthwise convolution is the ``where in time'' step and a pointwise convolution is the ``which
channels'' step. Splitting them is the whole reason the encoder is small. One \emph{unit} chains the
two:
\begin{equation}
  \mathcal{U}(\mathbf{h})
  = \operatorname{Drop}\Big(\operatorname{ReLU}\Big(\operatorname{BN}\Big(
      P\Big(\textstyle\sum_{k \in \mathcal{K}} D_k^{(\delta)}(\mathbf{h})\Big)\Big)\Big)\Big),
  \qquad \mathcal{K} = \{5, 11, 23\},
  \label{eq:unit}
\end{equation}
and one block runs two units and adds the input back:
\begin{equation}
  \operatorname{Block}(\mathbf{h}) = \operatorname{ReLU}\big(\mathbf{h} +
  (\mathcal{U} \circ \mathcal{U})(\mathbf{h})\big).
  \label{eq:block}
\end{equation}
Zero ``same'' padding is used everywhere, so the length $\nsteps$ never changes (goal~G3). Block $i$
uses $\delta_i = \min(2^i, \delta_{\max})$, which grows the receptive field quickly but keeps it
local (goal~G4).

In words, \Cref{eq:unit} looks at the same signal at three time scales at once. A kernel of size 5
sees a narrow local pattern, a kernel of size 23 sees about four times as far, and their outputs are
simply added, so the block never has to pick one scale in advance. $P$ then combines what the three
kernels found. BatchNorm \citep{ioffe2015batchnorm} keeps the activations on a stable scale, ReLU
adds the non-linearity, and dropout regularises.

\paragraph{Why this is small.}
A standard convolution with $\dmodel$ input and output channels and kernel size $k$ costs
$\dmodel^2 k$ weights. A depthwise-separable pair costs only
\begin{equation}
  \underbrace{\dmodel k}_{\text{depthwise}} \;+\; \underbrace{\dmodel^2}_{\text{pointwise}}
  \;\ll\; \dmodel^2 k .
  \label{eq:sep_cost}
\end{equation}

Counting the weights of \Cref{eq:unit} directly from the code, with the base width $\dmodel = 128$
and kernels $\{5,11,23\}$: the three depthwise convolutions together cost
$\dmodel \cdot 6 + \dmodel \cdot 12 + \dmodel \cdot 24 = 5{,}376$ weights, counting one bias per
channel. The pointwise convolution alone costs $\dmodel^2 + \dmodel = 16{,}512$ -- already three
times more than all three depthwise convolutions put together. Adding BatchNorm's $2\dmodel = 256$,
one unit costs $22{,}144$ parameters, one block (two units) costs $44{,}288$, and the full six-block
encoder plus its stem costs about $266{,}752$. That matches the $269{,}083$ measured for the wide
base model in the leaderboard, the small remainder being the pooling head.

A standard, non-separable convolution looking at the same three kernel sizes would instead cost
$\dmodel^2 \cdot (5{+}11{+}23) = 638{,}976$ weights for that same step -- about $29\times$ more.
That factor is why goal~G1 is reachable at all.

\subsection{Encoder variants}
\label{sec:arch:variants}

I built several encoders on top of the same block. Each paragraph below has the same shape: the
problem it attacks, the change in one equation, and what I expected. Results are in
\Cref{sec:results}, and \Cref{tab:encoder_variants} in the appendix lists every variant with its
parameter count, so this section can stay about the ideas.

Two symbols are shared by all of them. $\odot$ multiplies element by element, and $[\,\cdot\,;\,
\cdot\,]$ stacks two sets of channels on top of each other. Every equation below is written in the
same order the code runs it, so a reader who opens the implementation finds the same steps.

\paragraph{Bottleneck.}
The pointwise convolution dominates the parameter count, because it alone costs $\dmodel^2$. So I
split it into two cheaper $1\times1$ convolutions through a narrow middle of width
$r = \dmodel / 4$: first squeeze $\dmodel \to r$, then expand $r \to \dmodel$,
\begin{equation}
  P = P_{\text{expand}} P_{\text{squeeze}}, \qquad
  P_{\text{squeeze}} \in \R^{r \times \dmodel}, \quad
  P_{\text{expand}} \in \R^{\dmodel \times r},
  \qquad \text{cost } \dmodel^2 \rightarrow 2\dmodel r .
  \label{eq:bottleneck}
\end{equation}
With $r = \dmodel/4$ the pointwise cost becomes $2\dmodel(\dmodel/4) = \dmodel^2/2$ -- exactly half,
whatever $\dmodel$ is. At the size used in the experiments ($\dmodel = 64$, 4 blocks) this cuts the
whole model from 57{,}580 to 41{,}324 parameters, a real 28\,\% saving on the entire encoder and not
just on the pointwise step. This is the cheapest encoder I built and the one in my headline result.

\paragraph{Gated.}
Not every feature channel matters for every series. Here one summary of the whole series decides
which channels to trust. After the blocks have produced $\mathbf{h}$, squeeze time away into one
vector $\mathbf{s} \in \R^{\dmodel}$, turn it into a gate, and re-weight every time step with it:
\begin{equation}
  \mathbf{s} = \operatorname{summary}_j(\mathbf{h}) ,
  \qquad
  \mathbf{g} = \sig(W_g\,\mathbf{s}) \in [0,1]^{\dmodel} ,
  \qquad
  \mathbf{h}'_j = \mathbf{h}_j \odot (1 + \mathbf{g}) .
  \label{eq:gate}
\end{equation}
Two details of \Cref{eq:gate} are deliberate. First, $\operatorname{summary}_j$ is one of three ways
of squeezing time -- the maximum, the mean, or the last time step -- and I trained all three under
the same recipe so they could be compared. Second, the multiplier is $(1 + \mathbf{g}) \in [1,2]$,
not $\mathbf{g}$ alone. A plain multiply would let the gate flatten features towards zero; keeping
the original $\mathbf{h}$ and only \emph{amplifying} means the differences between time steps, which
are exactly what AOPCR and NDCG measure, survive untouched. The gate has no time index, so it turns
channels up or down and never touches the time axis.

\paragraph{Input gate.}
Same idea at a finer grain: the gate is read straight from the raw input, so it can change at every
time step,
\begin{equation}
  \mathbf{g}_j = \sig\!\big(W_g \ast \bag\big)_j \in [0,1]^{\dmodel},
  \qquad
  \mathbf{h}'_j = \mathbf{h}_j \odot (1 + \mathbf{g}_j) ,
  \label{eq:input_gate}
\end{equation}
where $W_g \ast \bag$ is a small convolution (kernel size 7) over the raw series. Compare the two
subscripts: \Cref{eq:gate} has \emph{one} gate $\mathbf{g}$ for the whole series, built from deep
features, while \Cref{eq:input_gate} has a gate $\mathbf{g}_j$ per time step, built from the raw
signal. That is the only difference. I tried both because they attack the same idea at two
granularities -- coarse against fine -- and comparing them says which one the gating idea actually
needs.

\paragraph{Spike / trend.}
Some evidence is a slow trend, some is one sharp jump, and a single convolution stack is biased
towards the smooth kind. So this variant runs two branches and glues them together:
\begin{align}
  \text{trend}_j &= \text{Encoder}(\bag)_j \in \R^{\dmodel} ,
  \label{eq:spike_trend}\\
  \text{spike}_j &= \operatorname{ReLU}\!\big(\operatorname{BN}(\operatorname{Conv}_3(
  \bag - \operatorname{avg}_w(\bag)))\big)_j \in \R^{d_{\text{spike}}} ,
  \label{eq:spike_branch}\\
  \mathbf{h}_j &= P\big([\text{trend}_j \,;\, \text{spike}_j]\big),
  \qquad
  \mathbf{h}'_j = \mathbf{h}_j \odot (1 + \mathbf{g}) \ \text{ as in \Cref{eq:gate}} .
  \label{eq:spike_mix}
\end{align}
The trend branch is the usual encoder, unchanged. The spike branch subtracts a local moving average
$\operatorname{avg}_w$ (window $w = 5$) from the raw series, so what is left is near zero on smooth
stretches and large only where the signal jumps; a small kernel-3 convolution turns that into
$d_{\text{spike}} = 16$ channels. The two branches are stacked, mixed back to width $\dmodel$ by a
$1\times1$ convolution, and then passed through the same summary gate as above.
\Cref{tab:ablation_encoder} shows this was the weakest of my real encoders, so the idea did not pay
off.

\paragraph{Reconstruction residual.}
This one asks a different question: what does the encoder \emph{fail} to explain? A $1\times1$
convolution tries to rebuild the raw input from the trend features, that rebuilt copy is subtracted
from the real input, and what is left over becomes $d_{\text{res}} = 16$ extra channels mixed back
in:
\begin{equation}
  \widehat{\bag} = P_{\text{rec}}(\text{trend}), \qquad
  \mathbf{h}_j = P\big([\,\text{trend}_j \,;\, \phi(\bag - \widehat{\bag})_j\,]\big),
  \label{eq:recon}
\end{equation}
with $\phi$ the same small convolution + BatchNorm + ReLU used for the spike branch. The residual
$\bag - \widehat{\bag}$ marks the parts of the signal the smooth features could not account for,
which is a reasonable place to look for an unusual event. There is no separate reconstruction loss:
the branch is learned end to end, so it is really a learned residual feature. It was the second
strongest encoder in my ablation (\Cref{tab:ablation_encoder}).

\paragraph{Multi-scale channels (a wrapper, not an encoder).}
Rolling max, min and standard deviation over several windows are appended as extra input channels,
so the network gets local statistics for free:
\begin{equation}
  \bag^{+} = \Big[\, \bag \,;\; \big(\text{roll\_max}_w(\bag)\big)_{w \in \mathcal{W}} \;;\;
  \big(\text{roll\_min}_w(\bag)\big)_{w \in \mathcal{W}} \;;\;
  \big(\text{roll\_std}_w(\bag)\big)_{w \in \mathcal{W}} \;;\; \operatorname{sign}(\Delta \bag) \,\Big] ,
  \label{eq:mschan}
\end{equation}
with $\mathcal{W} = \{3,7,15,31\}$ (all odd, so each window stays centred) and
$\Delta \bag_j = \bag_j - \bag_{j-1}$. This does not replace an encoder: it only widens the input
from 1 channel to $1 + 4 \cdot 3 + 1 = 14$ channels before handing it to any encoder above. Max, min
and standard deviation are used rather than a rolling mean on purpose -- a mean is \emph{linear}, so
the stem convolution could learn it by itself, while the other three are non-linear and genuinely
add something a convolution cannot compute. One BatchNorm normalises the 14 channels first, because
they do not share the raw series' scale; skipping it cost accuracy.

\paragraph{Multi-scale pyramid (a wrapper, not an encoder).}
The same encoder runs on the series downsampled by 1, 2, 4 and 8; the outputs are stretched back to
length $\nsteps$ and fused:
\begin{equation}
  \mathbf{h}_j = \sum_{s \in \mathcal{S}} \alpha_j^{s} \, \mathbf{h}_j^{(s)} ,
  \qquad
  \alpha_j^{s} = \operatorname{softmax}_{s}\big(\text{score}(\mathbf{h}_j^{(s)})\big),
  \qquad \sum_{s \in \mathcal{S}} \alpha_j^{s} = 1 ,
  \label{eq:pyramid_fusion}
\end{equation}
where $\mathcal{S} = \{1,2,4,8\}$ and the softmax normalises over the \emph{scale} axis, never over
time, so the per-time-step signal AOPCR and NDCG need is untouched. One encoder is shared across
every scale, so the parameter count barely moves and the extra cost is mostly compute (about
$1.9\times$). This was my attempt at the 1-D version of multi-magnification whole-slide-image MIL
\citep{hashimoto2020msdamil}, and it is the weakest thing I built (\Cref{tab:ablation_encoder}). It
also needs one constraint to work at all: the wrapped encoder must stay shallow enough that its
receptive field does not exceed $\nsteps / \max(\mathcal{S})$, or the coarsest scales collapse to a
nearly constant signal. That is why the pyramid uses a shallow 2-block base, and why the pipeline
checks the condition automatically for any new combination.

\subsection{Why this design and not another}
\label{sec:arch:why}

I considered three other directions and rejected each for a concrete reason.

A \textbf{Transformer encoder} was the obvious alternative to a convolutional stack, and it fails
both goals at once. Full self-attention costs $\mathcal{O}(\nsteps^2)$ in time and memory, and these
series run to 1000--1500 points, far too expensive for the microcontroller target
(\Cref{sec:context}). Worse, unrestricted attention lets any time step attend to any other, which is
the opposite of goal~G4: an output built from evidence smeared over the whole series gives an
importance map nobody can trust.

\textbf{Pruning or quantising InceptionTime} would shrink a network but not fix the real problem
from \Cref{sec:bg:tsc} -- it still ends in global average pooling, which destroys the per-time-step
information before the classifier sees it, so it would still need a post-hoc explainer.
\textbf{Keeping a bigger backbone and explaining it afterwards} fails for the same reason \millet{}
gives: a post-hoc explanation is not guaranteed to match what the model computed
(\Cref{sec:bg:related}). Every encoder here keeps the MIL contract of \Cref{eq:encoder_generic}
exactly, so any pooling head from \Cref{sec:pooling} turns it into a faithful, built-in explanation
instead.
